# Developing pi-egregore

This is a private, locally loaded Pi package. Before changing a surface, read `README.md`, `docs/ARCHITECTURE.md`, and its component README. Consult the installed Pi documentation and examples before changing Pi APIs or terminal UI behavior. This checkout is the suite source; the older personal Home directory was removed, while the older Tasks directory under `~/.pi/agent/extensions/` remains excluded from loading. See `docs/MIGRATION.md` for the current inventory and historical switch. Do not edit them for suite changes.

## Start here

The suite supports a conversation-driven flow: explore possibilities with Quests, organize chosen work with Tasks, resolve consequential decisions with Ask, and present their sourced state through Egregore and Frame. Read the root README for purpose, `CONTRIBUTING.md` for setup and host overrides, and `docs/ARCHITECTURE.md` for ownership. `docs/README.md` is the documentation map; `docs/POSITIONING.md` supplies product vocabulary. Distinguish implemented behavior, design intent and verified evidence.

Before editing, inspect `git status --short`, the current branch and staged changes. Identify the requested outcome and the component that owns it; preserve existing work. Read the affected component guide and implementation, then make the smallest coherent change. Documentation-only work should verify claims and links; runtime changes need the relevant component tests and full suite. Do not turn a documentation request into implementation, installation or publication.

## Ownership

- **Frame** (`packages/pi-frame`): reusable drawing primitives and opt-in presentation rules. It does not own application state, native input, layout, or tool execution.
- **Egregore** (`extensions/pi-egregore`): Composer, transcript adapters, workspace host, and the `/egregore` appearance editor. Preserve Pi's native editor and the installed pi-vim instance.
- **Tasks** (`extensions/pi-tasks`): plans, history, the `tasks` tool, and the independent no-Egregore fallback. Egregore displays sourced Tasks data; it does not create or complete plans.
- **Quests** (`extensions/pi-quests`): cross-session SQLite journal, pursuit lifecycle, goals, developments, evidence, connections and exploratory questions; `quests` and `/quests`. Explicit conversational pursuit records source-message provenance without resending work. Saved possibilities are distinct from accepted pursuits. Quests links Tasks plans but does not own their checklist or Ask approvals.
- **Ask** (`packages/pi-ask`): question/answer behavior, focus, and temporary input. Egregore hosts its visual settings room, not its answer semantics.
- **Contracts** (`packages/pi-agent-contracts`): the data-only, versioned dock and posted-question protocols consumed through `pi-agent-contracts/dock` and `pi-agent-contracts/posted`. **Shared adapters** (`lib/`): Frame integration, the shared task frame and the suite-local session-activity event contract. Keep component-specific state and lifecycle with the component that owns them.

For a cross-component change, identify the **state owner, visual adapter, settings authority, and fallback** before editing. Change only the owners required by the request. Do not make Frame a global renderer or assume every surface shares the same slots or input contract.

### State, integration and source map

- `package.json` is the package-entry and bundled-library authority. It loads Egregore, Tasks, Ask and Quests once. Keep independently installable packages from being registered twice.
- Egregore `workspace-runtime.ts` owns mounted UI lifecycle; `footer.ts` and `footer-settings.ts` own preferences and their editing transaction; `session-activity.ts` owns the branch-local activity feed and `/activity`.
- Tasks `book.ts` owns plan-library restoration/mutation; `requirements.ts` owns request coverage; `reconciliation.ts` builds completion-review guidance, while `index.ts` owns eligibility/lifecycle.
- Quests `store.ts` owns transactional records and history, `context.ts` validates current-branch source references and reads Tasks snapshots, `index.ts` owns tools/browser actions, and `surface.ts` owns journal presentation. The journal persists across branches; Tasks, posted questions and activity follow the session branch. Keep current data distinct from historical snapshots.
- Quests and Tasks publish activity facts; Egregore displays them. Current Quests Tasks-linking reads Tasks' branch records, and Egregore source inspection lazily loads Quests helpers. These are internal suite integrations, not a public plugin API; changes must preserve standalone loading and fail gracefully when optional sources are unavailable.
- Frame adapters in `lib/frame.ts` and Ask's package-local adapter handle cached implementation/export compatibility. Consult them before adding imports or another frame renderer. Keep one settings authority per field.
- Use `docs/PRIMITIVES.md` for published data contracts, `docs/decisions/` for ownership decisions, and `docs/ACCEPTANCE.md` for dated evidence. A test, source observation or model report establishes only the behavior it actually checks.

## Appearance and `/egregore`

Read `docs/SURFACE-WORKSPACE.md` and `extensions/pi-egregore/FOOTER.md` before adding a visual setting or appearance editor. `/egregore` has Input, Tasks, Ask, Transcript, More settings and General sections. Extend the appropriate room rather than creating a competing control. The detailed supported elements and constraints live in those documents; keep them authoritative rather than duplicating their inventory here. Keep selection-to-preview correspondence across rooms: derive target rectangles from actual rendered content, highlight only affected regions, preserve semantic foregrounds, and explain unavailable targets. Hover inspection is ephemeral and must not activate controls, steal keyboard focus, edit preferences or start timers. A shared appearance entry does not authorize taking over a self-rendering tool; extension surface registration remains a proposal until its owner, validation and native fallback are implemented and tested.

`pi-egregore.json` is the versioned visual-preference authority for these sections, including session-activity visibility and color; `pi-workspace.json`, then `pi-footer.json`, are read-only legacy fallbacks until the first Save. They share one Save/Undo/Discard transaction for that file. `pi-composer.json` owns Composer enablement (with a read-only `pi-home.json` fallback); `pi-tasks.json` owns Tasks enablement and standalone fallback preferences. Branch-sensitive task and run data stay in session entries. Do not introduce two live settings for the same field or claim an atomic Save across files without implementing and testing it. Validate versioned settings; do not silently overwrite malformed files or unknown newer versions.

Egregore's private room/control builders supply pure candidate patches; `footer-settings.ts` retains one accepted draft, transaction and interaction controller. Hover/keyboard audition uses cloned visuals or synthetic modes, never accepted preferences or Undo. Current-value restoration must not introduce default sections; Save must exclude an unaccepted candidate. Keep menu hit coordinates stable across preview-height changes and clear audition on blur, resize, invalidate, abort and disposal. Native message facts belong behind `native-message-adapter.ts` with guarded shapes and native fallback, not additional private-field casts. Review all six sections and companion entry points through `docs/SETTINGS-REVIEW.md`; do not promise a shared transaction/hover contract for native or third-party settings.

Previews are display-only and visibly labeled as such. Never alter the native draft, answers, plans, messages, tool results, recorded times, or run state to demonstrate a style. Preserve native cursor/IME, Vim undo and completion, keyboard and mouse mapping, narrow-width behavior, and native fallbacks for images and self-rendering tools. Motion follows real work, stops for blocking interactions, and cleans up on hide, reload, and disposal; do not add an idle animation loop just for decoration.

## Version control and collaboration

- Inspect working-tree and staged diffs before editing or committing. Another session may be working in the same checkout or pushing to the remote. Never infer ownership from file proximity, and never stage everything simply because it is modified.
- Commit only authorized, coherent changes and their necessary documentation/tests. Review `git diff --cached` as well as `git diff --cached --name-only`; scan for credentials, personal session/quest databases, preferences, captures and unrelated edits. Use a clear scoped commit message describing the result.
- Commit, push, publish and installation changes are separate actions. Perform only the actions requested; a local commit is neither a push nor a package release. Preserve user archives and existing history.
- Before an authorized push, fetch and inspect divergence. If the remote has advanced, preserve its changes; do not force-push, discard work or blindly pull/rebase a dirty shared checkout. A temporary clean worktree can apply a scoped commit on top of the remote without disturbing local edits. Report the pushed commit and any remaining local/remote divergence.
- Run checks against the state you intend to commit. Passing tests on a dirty tree can depend on uncommitted files; they do not prove a partial commit is self-contained. For partial runtime commits, verify an isolated worktree or explicitly leave that uncertainty unresolved.
- Keep generated dependencies, private runtime data and local installation configuration out of Git. The ignore file is a guard, not a privacy audit. Update the changelog for releasable behavior changes; keep historical acceptance records dated rather than rewriting them as fresh evidence.

### Portable tests: `npm test` runs on Windows, Ubuntu and macOS

`.github/workflows/test.yml` runs the whole `npm test` chain on a three-OS matrix for every push, so **one host passing is not cross-platform evidence**. A test must pass on all three or declare its platform condition explicitly; never assert platform-dependent behaviour conditionally. Keep these rules when adding or changing tests:

- **Never hardcode a path that must exist.** `/bin/sh`, `/usr/bin/…`, `/tmp/…` and `/opt/…` are POSIX-only, so a fixture that resolves them fails on Windows with `undefined`. Use `process.execPath` for "an existing absolute path", `join(tmpdir(), …)` for scratch locations, and `mkdtemp` for writable directories.
- **Never hardcode a separator.** `node:path` resolves per host, so `join`/`dirname`/`resolve` must build both the value under test and its expectation; compare against the same `join` the production code calls. A literal like `"/tmp/xdg/pi-dictation"` silently encodes the author's host and reads as green locally while failing on Windows, where the same call returns `\tmp\xdg\pi-dictation`.
- **Native `import()` needs a URL.** Use `import(pathToFileURL(join(source, "file.mjs")).href)`; a bare Windows path throws `ERR_UNSUPPORTED_ESM_URL_SCHEME`. Only `jiti.import(...)` accepts a raw path. Import host helpers once at the top of a test file instead of re-importing them inside a test.
- **Don't hide one platform bug behind another.** Assertions after the first failure in the same `test()` never run, so a POSIX fixture early in a test can mask further Windows bugs and make the reported failure count look smaller than it is. Keep independent platform-sensitive assertions in separate `test()` calls, or fix the whole group before trusting a "N failures" report.
- Genuinely POSIX-only behaviour (spawn errno codes, `/bin/sh` scripts, `chmod` semantics, newline filenames) stays tested behind an explicit `t.skip("reason")` for that platform; the skip is part of the documented baseline, not a workaround.
- Anything that touches the filesystem gets a unique `mkdtemp` path under `tmpdir()` with bounded async cleanup, and never assumes `.cmd`/`.bat` shims or a login shell.

When a Windows failure is reported, reproduce the expectation with `path.win32.join` (or `node:path/win32`) instead of guessing, then fix the fixture rather than the assertion's platform condition.
