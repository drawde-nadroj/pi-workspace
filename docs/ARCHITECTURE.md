# Architecture and ownership

This document explains how the suite composes one experience without merging domain-state or native-input ownership. For user procedures and lookup, start at [the documentation index](README.md). It describes the current ownership boundaries. The repository root is now a **private installable Pi package**, but a shared visual-customization API has not yet been implemented.

```text
Tasks plan/history state ── versioned data-only dock events ──> Workspace UI host
Ask question/answer state ── owns temporary input surface
Workspace layout + appearance preferences ──> Frame rendering primitives/presentation
Tasks native fallback ──> shared task-frame adapter ──> Frame
Ask question surface ──> package-local Frame loader ──> Frame
```

- **Frame** (`packages/pi-frame`) owns `frameRows`, `frameRail`, `paintFramePerimeter`, `statusPreset`, presentation rules, and the optional motion controller. Its optional `presentationRows` styles title/summary/hint rail labels bold while leaving ordinary body rows alone; consuming surfaces choose their own label colors. It does not infer task states, create timers by default, or replace Pi components globally. Public imports use `/primitives` and `/presentation`.
- **Workspace** (`extensions/pi-workspace`) owns its editor decoration, transcript adapters, `/workspace` interaction, preview transaction, and UI lifecycle. The six top sections (Input, Tasks, Ask, Transcript, More settings, General) own Tab/Shift-Tab navigation; Input properties stay within its section. Workspace alone owns the view-only advanced-control disclosure, contextual help and preview labels; none of these writes a preference or changes Ask/Tasks semantics. The standalone fixed-cell `/composer-preview` demo was retired: its fabricated footer/layout was not a source of truth for the live Composer. Composer appearance previews use the native editor in `/workspace`; motion prototypes must target the live frame rather than resurrecting that renderer. Before writing shared visual preferences, Workspace rejects stale on-disk workspace/legacy snapshots and unsupported Composer appearance versions (an optimistic check, not a cross-process lock). `appearance.ts` validates versioned input settings; `appearance-render.ts` lays out the input/footer. `footer.ts` writes versioned `pi-workspace.json` and reads `pi-footer.json` only as a legacy fallback, including Tasks *presentation*, Ask visuals and Workspace's versioned `transcript` chat/tool section, while Ask itself validates/reads its own section. `composer-controls.ts` owns `/composer` operational controls; `composer-preferences.ts` reads/writes `pi-composer.json`, falling back read-only to `pi-home.json` when the new file is absent. `workspace-runtime.ts` owns mounting and teardown through per-mount `surface-lifecycle.ts` scopes. The root manifest separately loads Ask; the appearance editor imports only its display-only preview/parser, not its question runtime.
- **Tasks** (`extensions/pi-tasks`) owns the `tasks` tool, `/tasks`, plan state/history and its independent no-Workspace widget. `pi-tasks.json` owns its enablement/fallback preferences. Session entries, not frame settings, store branch-sensitive task information. Tasks owns accepted-request records (immutable source/acceptance, explicit supersession, task links), their structural coverage checks, and its one-pass `agent_before_settle` checkpoint for agent-edited plans, including apparently closed task lists. The checkpoint asks the model to compare conversation requests against both the ledger and tasks; it is one hidden, bounded reminder with at most one additional model request per run, never automatic outcome mutation, broader authorization, or a loop. Uncovered requests and cancelled linked tasks prevent plan closure/agent archival; the read-only Q coverage view lives in Tasks, not Workspace. There is no new appearance preference. Payload version 3 retains the plans-v2 entry key so older readers fail closed; legacy records migrate without invented requirements. Semantic coverage and request interpretation remain model judgments. Settled reconciliation entries are filtered from later model context. Workspace merely displays sourced state.
- **Ask** (`packages/pi-ask`) owns the question tools, answer semantics, custom input, focus, versioned visual parser and synthetic shell preview. It reads the `ask` visual section of `pi-workspace.json` (or legacy `pi-footer.json`) once on opening a question, using the old `questionLabels` value only when no section is saved; it works without Workspace.
- **Shared adapters** (`lib/`) hold the versioned Workspace/Tasks dock event protocol, shared task frame, and local Frame reload adapter. Ask has a package-local reload adapter so it can remain independently installed.

Pi's public extension/TUI APIs and host-provided packages are the foundation. Workspace's Pi 1.0 transcript adapters also use guarded native internals; recheck them after host upgrades. Keep the native editor, Vim instance, draft, IME cursor, mouse selection and tool execution independent of visual styling. Support non-TUI modes without starting visual timers.

## Auxiliary recap authority

Workspace's optional recaps use `pi-recaps.json` and default off on missing/invalid configuration. `/composer` routes to the owner-native recap controls; `/recaps` saves separately and immediately. Opt-in discloses additional bounded OpenAI Codex/OAuth inference and subscription-resource use; off cancels queued/in-flight work. This is not part of the appearance transaction or task verification.

## Native Tasks–Ask thread

Tasks exposes **Work / Requests / Questions**. Work and request state remains Tasks-owned; question state remains Ask-owned. `posted-protocol.ts` is a passive version-1 data contract (question snapshots/open requests, Tasks link catalogue, non-blocking interaction tags), not a shared state database or renderer. Optional bounded catalogue titles/task names improve read-only context, and `attentionHosted` is distinct from link availability so hiding Tasks permits Ask's fallback cue. Legacy catalogues remain supported. Response kind is displayed separately from delivery phase; correction guidance preserves original records and does not promise to reverse delivered effects. Ask stays independently installable; Tasks works when Ask is not loaded and shows an unavailable inbox. Workspace owns the attention presentation and clock interpretation; Frame remains passive.

Ask's `question_queue` tool persists version-1 branch-local posted-question records under `pi-ask:posted-v1`. `/questions` is its standalone entry; `/tasks questions` selects Ask projections. The TaskPanel stays mounted under a raised Ask overlay. Ask reuses its existing native answer/review machinery and reads the existing Ask appearance/density once on opening. Nested Escape follows review/note/custom/clarification Back/Discard semantics; outer Escape preserves unsubmitted drafts, including clarification buffers. Urgency-only changes refresh displayed context without losing input; definition/session changes still reject submission. Explicit Submit records a response and queues Pi steering. Delivery is acknowledged only when the original submission is included in a model-context event. Application is an explicit agent report with consequence, never automatic task mutation. Stale revisions/session interactions fail closed. Withdrawal and replacement preserve provenance and never imply consent. Interrupted submissions are not automatically retried.

Tasks enforces only **linked agent task starts/completions** against unresolved projections (deferred questions become blocking through an Ask-owned needed-now transition at that boundary) and blocks agent archival with unresolved linked questions. This is not a generic tool/side-effect permission system. Independent authorized work can continue. Existing synchronous Ask remains the immediate blocking interaction. User task edits retain their own precedence. The Workspace overview's optional `questions` counts are validated separately from task progress; they do not manufacture task blockers or verification. `pi-workspace:interaction:v1` tags Tasks browsing and posted Ask as input-owning but non-blocking; Workspace still suppresses motion while focused dialogs own input, while tracking real independent work. Synchronous Ask and untagged blocking prompts still pause active time.

Historical tool results own post/disposition/application cards; custom submission messages own submitted-response cards; one immutable custom entry owns the delivery receipt. Defaults use progressive disclosure and readable wording. Tasks' display-only `transcript.ts` adapter owns neutral work titles with small status-colored glyphs, grouped request headings, bounded prose and exact-source/criterion disclosure. Shared coverage qualifications remain in the body rather than only in a clipping-prone frame rail; no record, outcome or appearance setting changes during rendering. The native browser and transcript share Tasks' `typography.ts` vocabulary; browser selection remains a separate caret/background, and grouped short-label details use the same bounded reading measure. Overview layout and question semantics are not replaced by this presentation grammar. Existing `/workspace` Tasks, Ask and Transcript boundaries remain authoritative—no new settings file or cross-file transaction. The Tasks room styles the persistent Workspace overview, Ask styles its shell, and Transcript's eligible adapters do not take over self-rendering Ask/Tasks bodies. No new live preference or native draft is used for demonstration.

## Harness guidance and evaluation

Tasks owns evidence-based stopping guidance through existing `doneWhen` and requirement acceptance fields. Its unchanged one-shot checkpoint distinguishes missing work, record-only updates, unresolved evidence/blockers, and unauthorized optional improvements; it still checks original conversation coverage even for closed plans. Ask owns shared answer-handoff guidance for both question tools: preserve notes/caveats, drop stale questions, and leave skips/unknown approvals unresolved. It does not automatically mutate Tasks or require Tasks to be installed. These are guidance contracts, not semantic guarantees or new lifecycle/schema behavior.

`eval/harness/` is a development-only, opt-in comparison kit with synthetic scenarios, a local artifact verifier, validated paired review records, and deterministic tests. It is not registered as an extension or packaged as a runtime component. No telemetry, session ingestion, paid model execution, or context-management policy is added. See `eval/harness/README.md` from the repository root for authorization, isolation, provenance, and evaluation limits.

## Optional Chronomancer journal mirror

`packages/chronomancer` is separately loaded, not registered by the root suite manifest. Chronomancer owns the Markdown journal observer, complete read-only mirror reader, and bounded above-editor launcher. `/chronomancer mirror read` projects all available saved days and full bodies with parent links in a temporary Pi overlay; it does not inject the journal into the Pi conversation, change capture mode, edit pass checkpoints, or replace the native composer. Viewer selection/scroll/follow state is ephemeral; there is no new visual-preference authority or Workspace/Frame state ownership. Regular Pi uses the same keyboard reader as fullscreen, with fullscreen mouse interaction as an extra path. Invalid source files produce warnings rather than silently disappearing. Editable cross-session inline journal roots remain outside this reader's contract.

## Native copy feedback

Workspace's private `copy-flash.ts` adapter frames only Pi 1.0's exact fullscreen `Copied!` success row with passive Frame primitives. Pi owns flash state, clipboard operations, expiry and top-right composition; Workspace owns only this reversible render decoration while Composer is enabled. No new preference or input handler is introduced. Other notices, unsupported shapes, narrow widths and insufficient screen height retain native rendering. Teardown restores only the adapter's own patch and leaves retained wrappers inert.

`copy-selection.ts` owns the private fullscreen copy adapter and a weak, per-component record of the latest supported frame geometry. Chat, grouped tools and ordinary/web tool adapters register their rendered rows; Frame remains passive and unchanged. The copy adapter follows the native scroll-content Container mouse layout without rerendering, validates exact source rows and native extraction, then excludes only registered rails, sides and added padding. It preserves literal pipes and border-like content and leaves regular mode, fixed docks, self-renderers and unsupported/stale layouts native. No clipboard backend, selection input, preference file or timer is replaced. Copy feedback uses an achromatic light/dark border and ordinary theme text instead of accent/success colors.

## Workspace selection adapter

Workspace owns persistent selection and optional static hover inspection in the four `/workspace` appearance rooms. `preview-selection.ts` adapts synthetic Tasks/Ask/Transcript rows using actual rendered rectangles and discovered perimeters; it never opens Ask, edits Tasks or writes preferences. Native Composer retains `appearance-render.ts` and its existing editor instance. Inspection/focus are ephemeral; only accepted property edits enter the bounded Undo/Save transaction. Selection backgrounds track the actual foreground SGR color so user identity, custom colors and failed statuses remain unchanged and readable. Fixed preview labels can remain inspectable without being highlighted as affected by a control. Input, hover and pulse resources clear on the documented lifecycle boundaries.

The proposed central Transcript catalogue covers codemode, edit/write, web results and extension-submitted messages through owner-approved adapters, not a universal renderer or tool interception. Its scope and prospective contract live in [the surface specification](SURFACE-WORKSPACE.md#proposed-transcript-catalogue); there is still no public registration API or duplicate preference authority.

## Implemented private refactors and registry boundary

1. Workspace's private `workspace-input-room.ts`, `workspace-message-rooms.ts`, `workspace-preference-rooms.ts` and existing `task-settings.ts` build controls through `workspace-room-types.ts`. `footer-settings.ts` retains the single draft, Undo/Save/Discard transaction, navigation, hit testing, audition and lifecycle. `workspace-setting-layout.ts` owns display-only vocabulary/columns; `workspace-general-preview.ts` owns explicitly synthetic name/spacing examples. The pure Workspace-owned `message-spacing.ts` applies the existing density to live user/assistant bodies and General/Transcript samples: Compact adds no edge rows, Spaced adds one above and below. `sent-messages.ts` normalizes only native padding and translates mouse coordinates; internal content gaps and native fallback remain intact. They do not centralize Ask/Tasks domain state or create a public registry.
2. `native-message-adapter.ts` supplies read-only typed facts for `sent-messages.ts` and `grouped-tools.ts`. It guards native methods, private-field shapes, content/call records, streaming and positive creation timestamps on every read. Unsupported/throwing or drifted shapes use native rendering; disposal restores only owned patches. Workspace's full entry now passes strict typing; the four previously recorded native-field diagnostics are resolved. Native classes remain host-owned, not a new public dependency contract.
3. Choice audition clones visual preferences or uses a synthetic state, separate from the accepted draft, real run and Undo. Current-value restoration avoids introducing default sections into an otherwise unchanged candidate. Menu geometry is stable within a terminal size; blur/resize/invalidation/close restore audition. Save accepts only the draft. Workspace still owns one settings file transaction; companion Workspace/Tasks preferences save separately.
4. `loadWorkspacePrefs` rejects unknown Tasks section/presentation versions before `footerPrefs` can normalize them away. Ask/Transcript retain their existing read-only/Save-blocking behavior. No schema version or live settings file is migrated by this change.
5. Prove representative owner-approved tool/message adapters before exposing the proposed catalogue registration contract. Keep runtime preference and theme authorities singular; adapter discovery must not imply permission to intercept execution or replace self-rendering content.

The first two refactors and all-settings improvements were explicitly authorized and implemented. The larger registry/front-door remains proposed. See [the complete settings review](SETTINGS-REVIEW.md) and [fresh acceptance evidence](ACCEPTANCE.md).

## Intended customization boundary

Grow `/workspace` into an opt-in **surface workspace** without making Frame a global layout manager. A surface adapter should define stable element IDs, supported slots, defaults, semantic state facts, collision priorities, preview samples and validated versioned preferences. A shared interaction layer can provide keyboard/mouse selection, live previews, Save/Undo/Discard and rollback. The surface still owns content, input, hit targets, lifecycle, and redraw. Preview facts must be explicitly labeled and never written to tasks, answers, drafts or timestamps.

Start by extracting only proven common mechanics. Composer has six rail positions *and* footer rows; a question has a replacement input surface; Tasks has a body and overview; transcript tool cards can be self-rendering. Do not pretend every surface has the same slots. Give each screen a keyboard path, responsive/narrow fallback, theme contrast and reduced-motion safety.

## Dependency and installation rules

The private root `pi-workspace-suite` manifest explicitly lists `extensions/pi-workspace/index.ts`, `extensions/pi-tasks/index.ts` and `packages/pi-ask/extensions/questions.ts`, once each. The packed root bundles only `pi-embeddable-frame` under its own `node_modules`; Frame registers no extension. The host packages actually imported by suite sources (`@earendil-works/pi-coding-agent`, `@earendil-works/pi-tui`, `@earendil-works/pi-ai`, `typebox`) are peers, not bundled runtime dependencies. Frame and Ask retain their separate versioned package manifests, but must not be loaded a second time alongside the suite. Keep one authoritative source file for each module. Packed install, a real Pi RPC cold-start, repeat loader tests and an interactive `/reload` now pass. Live settings load this checkout once. The older personal Home directory and its exclusion were removed at the user's request; the older personal Tasks directory is still excluded. The original migration backup records the earlier switch, not this cleanup. Physical IME, human visual/motion review, real drag selection and authenticated turns remain unverified. See [migration](MIGRATION.md) and [acceptance](ACCEPTANCE.md).
