# Surface workspace specification

**Status: proposed design, not implemented across all surfaces.** This inventory distinguishes what already works from what the next implementation phases must add. The private suite remains isolated from the live Pi installation. See [architecture](ARCHITECTURE.md), [migration](MIGRATION.md), the existing [footer workspace guide](../extensions/pi-home/FOOTER.md), and the [Frame feature guide](../packages/pi-frame/FEATURE-GUIDE.md).

## Outcome and boundaries

A person can choose a supported **surface**, select a named visual element in a list or its preview, change visibility/placement/text treatment where safe, and inspect the result before Save. The same information is usable from the keyboard in regular terminal mode; fullscreen adds pointer targets. Developers can add a surface through documented semantic facts, settings validation, render/hit-target adapters and tests, without replacing the native Pi editor or making Frame own application state.

**This is a design system, not a universal layout engine.** Each surface declares its own supported slots, collision priorities and immutable content. Frame supplies six rail positions and passive drawing/presentation primitives where suitable. A question's answer editor, a Tasks plan browser and a self-rendering tool are not interchangeable frame bodies. The surface adapter owns render scheduling, focus, IME/mouse mapping and disposal. Defaults keep the current visual grammar until a user explicitly saves changes.

## Settings and migration contract

- Keep `pi-home.json` for Home look/enablement and `pi-tasks.json` for Tasks enablement and standalone fallback. Session entries remain the authority for branch-sensitive plans and clocks.
- Keep `pi-footer.json` as the **current visual preference authority** for Composer and Home's Tasks overview. Add separate, versioned `ask` and `transcript` visual sections only after defining their parsers and fallback behavior. The legacy filename is not a reason to move user preferences during the first iteration. `questionLabels` stays a compatible fallback until the new Ask section is saved; do not create two competing live settings for one field.
- Store only serializable visual rules, never demo state, timestamps, controller instances, answers, plans or editor text. Validate allowed IDs/positions, bounds, color contrast/syntax, Unicode/terminal-control stripping and schema versions. Missing sections preserve old defaults. Unknown newer versions or malformed files must not be overwritten implicitly by Save; report them and preserve their bytes until an explicit migration/repair decision.
- Keep a single transactional draft **per file**: preview in memory, Undo the settings edit, Save atomically, Discard/failed Save restore the baseline. If a future workspace edits both `pi-footer.json` and `pi-tasks.json`, either save each surface independently with a clear boundary or design tested cross-file rollback first. Do not imply an atomic multi-file Save that does not exist.
- Ask should read only its own visual section at question opening and continue to work without Home; the suite may host the settings UI while standalone Ask remains usable with safe defaults. Changing a preference in one Pi session does not rewrite an active question in another; other processes adopt saved preferences on reload/new interaction as documented.

## Workspace navigation decision (open)

| Approach | Advantages for users | Cost and extensibility tradeoff |
| --- | --- | --- |
| **One workspace with surface sections** | One place to discover Composer, Tasks, Ask and transcript controls; consistent selection and preview flow; easy to compare visual grammar. | A large screen can become crowded. It must not imply one renderer or one atomic Save across different preference owners. Standalone Ask needs safe defaults or an independent way to reach its controls without Home. |
| **Separate appearance commands per surface** | Small focused screens, each surface can own its Save and lifecycle; standalone packages have an obvious independent entry point. | Discovery becomes scattered and visual conventions can drift even if the code shares controls; `/tasks` already means plan/history management, so a new appearance command must not overload it. |
| **One front door with independent surface editors** *(proposed fit, not yet selected)* | Unified discoverability and consistent UI, while each surface keeps a focused preview, settings authority and Save/Discard scope. `/footer` can deep-link to its existing view; independent packages can expose an entry to their own editor if needed. | Requires a small navigation contract and a clear indication of which surface has unsaved edits. The shell must not take ownership of Ask input or Tasks plans. |

A public surface-registration API or a new command name should follow a working internal adapter and an explicit naming decision, not precede them. Document how add-ons contribute a surface before calling this an extensible framework.

## Shared workspace mechanics (extract only after tests)

Keep `/footer` as a compatibility entry point. A unified navigation shell and any new command name are **not decided** here. For each surface adapter, require: stable element IDs and display names; supported slots and priority rules; a versioned validator/defaults; a render sample with cell-accurate hit targets; source/fallback conditions; and disposal hooks. The shared shell should own selection synchronization, list/search, keyboard and fullscreen mouse navigation, focus indication, choice/text editors, dirty state, bounded Undo, Save/Discard/failed-save rollback and the preview-only banner. The adapter owns native content and state facts. Do not extract a generic renderer from `/footer` merely because its UI code is long.

A preview may use synthetic **labeled** states for Tasks, Ask and transcript/tool frames; it cannot mutate native input, open a real question, start a task/run, send a message, record a time or invoke a model. When Home is off, the existing temporary Composer preview must restore the prior look on close. No idle animation loops; demo motion is explicit, disposable and quiet while typing or in blocking dialogs.

## Acceptance gates

1. **Data safety:** After open/change/Undo/Discard/failed Save, assert byte-for-byte unchanged plans, answers, transcript and native draft; saved visual preferences change only on successful Save. Verify unknown versions and malformed JSON survive untouched.
2. **Interaction:** List and preview select the same visible element; hidden elements remain searchable; keyboard works in regular mode; fullscreen mouse hits and scroll/resize do not drift. Focus/cursor/IME and Vim draft/undo/completion survive open/close and reload.
3. **Visual truth:** Check theme contrast, narrow and wide terminal-cell widths, ANSI/CJK/emoji labels, reserved native hints, semantic error/blocked cues and sourced creation times. Native/self-rendering/graphical fallbacks remain native.
4. **Lifecycle:** Test cold start, reload, unload, session switch/shutdown, question replacement, streaming and state changes. Controllers stop when hidden, unfocused, typing, blocked, motion-off or disposed. Non-TUI modes keep domain tools without opening custom components.
5. **Distribution and documentation:** Isolated packed-suite tests, standalone Ask/Frame and no-Home Tasks checks, one Git change per coherent feature, schema migration notes and a developer example linked from the Frame feature guide. Report automated tests and live-terminal checks separately before seeking approval for the live switch.
