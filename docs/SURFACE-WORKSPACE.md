# Surface workspace specification

**Status: four appearance rooms plus More settings and General implemented; private room builders and reversible audition implemented; third-party surface registration remains a design direction.** This inventory distinguishes implemented controls from future adapter work. After explicit approval, the private suite is loaded by the live Pi settings; the old personal Workspace directory was removed and the remaining old Tasks entry is excluded. See [architecture](ARCHITECTURE.md), [migration](MIGRATION.md), the [footer workspace guide](../extensions/pi-workspace/FOOTER.md), and the [Frame feature guide](../packages/pi-frame/FEATURE-GUIDE.md).

## Outcome and boundaries

A person can choose a supported **surface**, select a named visual element in a list or its preview, change visibility/placement/text treatment where safe, and inspect the result before Save. The same information is usable from the keyboard in regular terminal mode; fullscreen adds pointer targets. Developers can add a surface through documented semantic facts, settings validation, render/hit-target adapters and tests, without replacing the native Pi editor or making Frame own application state.

**This is a design system, not a universal layout engine.** Each surface declares its own supported slots, collision priorities and immutable content. Frame supplies six rail positions and passive drawing/presentation primitives where suitable. A question's answer editor, a Tasks plan browser and a self-rendering tool are not interchangeable frame bodies. The surface adapter owns render scheduling, focus, IME/mouse mapping and disposal. Defaults keep the current visual grammar until a user explicitly saves changes.

**Current boundary:** `/workspace` covers Composer and element-level selection in Workspace's Tasks, Ask and Transcript demos. Chat/tool settings deliberately cover only safe rails and tones, not arbitrary body/layout edits. Tasks appearance has placement controls, not arbitrary hide/reorder controls; that is deliberate until the semantics are specified. Extend the existing room rather than reimplementing it.

**Repeated frame vocabulary:** Frame owns the six corner/rail coordinates and truncation, not the meaning of a label. Workspace's `sent-metadata.ts` formats sourced Sent metadata (local time through seconds, not milliseconds) for the Composer's latest user send, each chat message's creation time, and grouped tool calls' issuing-assistant creation time. The `pi-workspace.json` Icons preference selects an outgoing-envelope glyph or readable `Sent` text for all three; Composer's directory uses the matching folder glyph or unadorned path. No separate per-surface icon toggle is stored. The Composer `sentTime` element and Transcript `chatSent` setting retain separate placement/visibility authorities; grouped tools follow the chat setting because their time belongs to the issuing assistant. Workspace's `toolIdentity` treatment is already shared by ordinary, grouped and allowlisted web tool rails, while status is deliberately placed in the ordinary header, web-card lower rail, or individual grouped child row. A tool status is not a Sent time, and a tool title/target is not a chat speaker. Do not unify source clocks, settings or slots merely because the rails look alike.

## Navigation and operational scope

When six full room labels do not fit, **Rooms…** exposes the complete list rather than omitting destinations. **Ctrl+R** opens it from normal drawer navigation; Tab/Shift+Tab remain fast paths. Room selection is ephemeral, not a settings edit. Workspace's separately saved recap opt-in is discoverable through `/composer` and `/recaps`, not an untested cross-file workspace Save.

## Connected preview contract

Workspace's `preview-selection.ts` is a display-only visual adapter, not a surface registry. It combines actual rendered label rectangles with discovered frame perimeters, then paints only the affected regions. All four rooms retain a static selected-target indication; labels use an underline, while perimeter selection excludes unrelated labels and includes visible side rails. Existing theme/custom foregrounds, weight, graphemes, widths and click coordinates are preserved. The brief selection pulse is interaction-owned; render calls never start it. Native Composer remains on its existing layout/hit adapter.

The inspector names the selected element and supported location. It explains hidden values, missing native facts, absent sample active rows/overflow, unsupported settings versions and clipped preview targets. Action/error messages take precedence over availability help. Sample-only facts remain labeled and are never written to domain state. Transcript regions can declare `affected: false`: fixed user identity and failed status remain inspectable/clickable, but assistant-name and successful-status edits do not highlight them as mutable targets. This is Workspace preview metadata, not a public extension API.

When fullscreen dispatch supplies pointer-move events, a hovered list element, property or rendered region temporarily becomes the preview's **Inspecting** target. It does not change keyboard selection/focus, draft preferences, Undo, plans or answers. Hover is static; leaving a target, keyboard interaction, blur, resize, invalidation or disposal clears it. Regular mode and terminals without hover retain the complete keyboard path. The editor does not enable a second mouse-reporting mode.

## Proposed Transcript catalogue

**Design direction only: no public registry, arbitrary tool override or new preferences are implemented by connected previews.** Keep `/workspace` → Transcript as the single appearance front door, with Messages, Tools and Details groups. Common defaults should be distinct from adapter-specific overrides; an adapter declares only the controls it can safely support. Do not add one competing appearance command or settings file per tool.

| Surface family | Candidate safe controls | Required invariant |
| --- | --- | --- |
| User/assistant messages | Existing identity, sourced metadata and density controls; later bounded layout controls | Preserve message roles/content, native selection and timestamp provenance; assistant creation is not completion. |
| Codemode and nested calls | Identity/status placement, summary/detail disclosure and code/output presentation where the owning renderer opts in | Preserve code, results and parent/child associations; a returned orchestration envelope does not prove all nested calls succeeded. |
| Edit and write | Metadata hierarchy, diff/line-number presentation, whitespace density and disclosure | Preserve exact changes, paths and diagnostics; never fabricate a previous file or hide destructive changes under a success style. |
| Web search/fetch | Source-list hierarchy, result density, metadata and expansion | Preserve URLs/citations, source provenance and real errors; styling must not imply a claim was verified. |
| Extension-submitted messages/custom entries | Opt-in identity, supported frame/metadata slots and density | Preserve custom message content, context-inclusion behavior, application/delivery provenance and sourced time. |
| Unknown, graphical or self-rendering tools | Native fallback unless the owner explicitly supplies an adapter | Do not coerce the renderer, intercept tool execution or break native expansion/mouse mapping. |

An eventual versioned adapter contract should declare a stable namespaced `surfaceId`, content kind, safe capabilities/slots, semantic facts, defaults and validation, owner-specific preference scope, display-only sample/hit regions, render integration/fallback, invalidation and idempotent disposal. Shared chrome may resolve settings and selection, but each adapter owns its content and input contract. Surface existence must not be inferred solely from a tool name: built-in text, custom self-renderers, nested codemode and submitted messages use different integration paths. Existing native Pi theme roles remain the fallback rather than a second theme authority.

Before making that API public, prove it with representative code/data/diff/search/custom-message adapters and test unknown versions, semantic failures, reload/unload, standalone behavior, mouse/expansion, Unicode and narrow layouts. Preview fixtures must be synthetic and perform no model/tool/network calls. A settings transaction must retain the existing file authority and cannot claim atomicity across additional files without tested rollback. This catalogue is proposed scope for a later authorized slice; the current Transcript room still exposes only its documented chat/tool rails and tones.

## Tasks–Ask cross-surface cohesion

The native Tasks browser now has Work, Requests and Questions views. Requests show original wording and satisfaction criteria only in selected details; Questions opens Ask above the retained Tasks panel. This is behavior/navigation, not a new appearance editor. The Tasks room continues to style the Workspace **overview**, whose question counts/attention row are sourced separately from task completion. Ask's posted overlay uses the existing Ask shell title, placement/emphasis/hints and shared density at opening. Transcript retains its documented eligible-adapter scope; new Ask event cards remain self-rendering and do not invent creation times or silently rewrite earlier events.

The versioned question state lives in session entries, not `pi-workspace.json`. Theme/selection/urgency labels remain consistent across surfaces without merging owners or input contracts. Input & footer's native preview and Save/Undo/Discard transaction are unchanged. Tasks browsing and posted question overlays suppress motion but do not falsely label independent work as waiting; synchronous Ask still pauses. No new appearance preferences or competing controls were introduced. Standalone Ask and Tasks without Workspace retain their native paths.

## All-settings layout and audition

All six sections use bounded explanations and aligned Part / Setting / Value vocabulary; empty prefixes show None. More settings has view-only Footer, Context, Git, Activity & time and All settings filters. The [complete settings review](SETTINGS-REVIEW.md) covers individual controls and companion entry points, including separate immediate Workspace/Tasks saves and native/third-party limits.

Workspace's private room builders provide pure candidate patches through one controller. Hover or arrows audition safe state/color/position/spacing choices; `✓` stays the configured value, `›` stays keyboard focus. Click accepts the pointed option; Enter accepts the keyboard option. Moving off restores keyboard audition; Escape/blur/invalidate/resize/abort/disposal restore prior appearance. Hover never starts timers, opens input or modifies a real run, draft, message, answer or Undo. Save includes only accepted edits. Menu coordinates are locked per terminal size when examples change height. General's name/spacing messages are visibly synthetic. Unsupported hover reporting retains a complete keyboard path.

## Settings and migration contract

- Use `pi-composer.json` for Composer operation, with `pi-home.json` as a read-only legacy fallback and `pi-tasks.json` for Tasks enablement and standalone fallback. Session entries remain the authority for branch-sensitive plans and clocks.
- Keep versioned `pi-workspace.json` as the **current visual preference authority** for Composer, Workspace's Tasks overview, Ask's question shell and Workspace's chat/tool metadata. The versioned `ask` section has an Ask-owned validator; `questionLabels` stays a compatible read-only fallback. Workspace validates the versioned `transcript` section; `messageTime` and `toolLabels` are read-only fallbacks until it is saved. Unknown future Ask/Transcript versions block Save rather than being overwritten. Unknown Tasks section/presentation versions fail before preference normalization; unsupported Composer/workspace versions also block loading/Save. Read `pi-footer.json` only if the workspace file is absent, and preserve the legacy bytes on Save; do not create two competing live settings for one field.
- Store only serializable visual rules, never demo state, timestamps, controller instances, answers, plans or editor text. Validate allowed IDs/positions, bounds, color contrast/syntax, Unicode/terminal-control stripping and schema versions. Missing sections preserve old defaults. Unknown newer versions or malformed files must not be overwritten implicitly by Save; report them and preserve their bytes until an explicit migration/repair decision.
- Keep a single transactional draft **per file**: preview in memory, Undo the settings edit, Save atomically, Discard/failed Save restore the baseline. If a future workspace edits both `pi-workspace.json` and `pi-tasks.json`, either save each surface independently with a clear boundary or design tested cross-file rollback first. Do not imply an atomic multi-file Save that does not exist.
- Ask reads only its own visual section at question opening and continues to work without Workspace; the suite hosts its settings room while standalone Ask retains safe defaults. Changing a preference in one Pi session does not rewrite an active question in another; other processes adopt saved preferences on reload/new interaction as documented.

## Workspace navigation: one front door, focused surface rooms

| Approach | Advantages for users | Cost and extensibility tradeoff |
| --- | --- | --- |
| **One workspace with surface sections** | One place to discover Composer, Tasks, Ask and transcript controls; consistent selection and preview flow; easy to compare visual grammar. | A large screen can become crowded. It must not imply one renderer or one atomic Save across different preference owners. Standalone Ask needs safe defaults or an independent way to reach its controls without Workspace. |
| **Separate appearance commands per surface** | Small focused screens, each surface can own its Save and lifecycle; standalone packages have an obvious independent entry point. | Discovery becomes scattered and visual conventions can drift even if the code shares controls; `/tasks` already means plan/history management, so a new appearance command must not overload it. |
| **One front door with independent surface editors** *(selected direction; Composer, Tasks, Ask and Transcript are the first rooms)* | Unified discoverability and consistent UI, while each surface keeps a focused preview, settings authority and Save/Discard scope. `/workspace` opens the existing view; independent packages can expose an entry to their own editor if needed. | Requires a small navigation contract and a clear indication of which surface has unsaved edits. The shell must not take ownership of Ask input or Tasks plans. |

The selected direction uses `/workspace` as the only appearance command; `pi-workspace.json` is the preference file for these rooms; the old filename is read only as a fallback. Its first four rooms are Input & footer, Tasks, Ask and Transcript, reusing the same transactional preview. **Today these four rooms share one atomic Save/Discard for `pi-workspace.json`**, which holds their separate visual sections; independent per-surface Save scopes matter when future rooms use different files. Tab and Shift+Tab follow the six top sections (Input, Tasks, Ask, Transcript, More settings, General); Input properties remain inside Input and open with Enter or Right. Undo stays with Save and Discard. Tasks and More settings show common controls first with an explicit Advanced settings expander; Tasks only shows controls for the selected part. Fixed Ask/Transcript frame identity is informational rather than an inert action. Labels describe visible outcomes without changing stored preference values. Narrow navigation uses **Rooms…** for the complete destination list and retains the current section number/name; **Ctrl+R** opens the same selector. It does not depend on silently omitted later tabs. Saves check whether the workspace or legacy preference file changed since load/open and refuse a stale write; this optimistic check is not an inter-process lock. A public surface-registration API still requires working adapters and an explicit contract. Document how add-ons contribute a surface before calling this an extensible framework.

## Shared workspace mechanics (extract only after tests)

Use `/workspace` as the front door with focused rooms in the existing shared interaction shell. For each surface adapter, require: stable element IDs and display names; supported slots and priority rules; a versioned validator/defaults; a render sample with cell-accurate hit targets; source/fallback conditions; and disposal hooks. The shared shell should own selection synchronization, list/search, keyboard and fullscreen mouse navigation, focus indication, choice/text editors, dirty state, bounded Undo, Save/Discard/failed-save rollback and the preview-only banner. The adapter owns native content and state facts. Do not extract a generic renderer from the settings editor merely because its UI code is long.

A preview may use synthetic **labeled** states for Tasks, Ask and transcript/tool frames; it cannot mutate native input, open a real question, start a task/run, send a message, record a time or invoke a model. When Workspace is off, `/workspace`'s temporary native-editor Composer appearance view must restore the prior look on close. The separate fixed-cell `/composer-preview` screen is retired and must not be reused as a live Composer reference. No idle animation loops; demo motion is explicit, disposable and quiet while typing or in blocking dialogs.

## Acceptance gates

1. **Data safety:** After open/change/Undo/Discard/failed Save, assert byte-for-byte unchanged plans, answers, transcript and native draft; saved visual preferences change only on successful Save. Verify unknown versions and malformed JSON survive untouched.
2. **Interaction:** List and preview select the same visible element; hidden elements remain searchable; keyboard works in regular mode; fullscreen mouse hits and scroll/resize do not drift. Focus/cursor/IME and Vim draft/undo/completion survive open/close and reload.
3. **Visual truth:** Check theme contrast, narrow and wide terminal-cell widths, ANSI/CJK/emoji labels, reserved native hints, semantic error/blocked cues and sourced creation times. Native/self-rendering/graphical fallbacks remain native.
4. **Lifecycle:** Test cold start, reload, unload, session switch/shutdown, question replacement, streaming and state changes. Controllers stop when hidden, unfocused, typing, blocked, motion-off or disposed. Non-TUI modes keep domain tools without opening custom components.
5. **Distribution and documentation:** Isolated packed-suite tests, standalone Ask/Frame and no-Workspace Tasks checks, one Git change per coherent feature, schema migration notes and a developer example linked from the Frame feature guide. Keep automated, isolated-terminal, live-configuration and human observations distinct; the authorized live switch does not resolve remaining physical and subjective checks.
